# 语雀权限模型 — agent 能管到哪一层（可行性探测）

> 结论先行：**agent 能管「内容 + 结构」，管不了「谁有编辑权」。**
> 语雀的权限配置是**知识库 / 团队**粒度，而且**只能人工在网页 UI 里点一次**——
> 官方 API 根本没有「知识库协作者」「目录只读」这类接口。
> 所以要达成「社员不能改指导文档 / 不能改归档目录 / 必须按模板填」，
> 必须用**「两库分离 + agent 巡检回滚」**的组合，而不是指望平台权限。

探测证据均来自 `lqogh0` 团队的写权限令牌实测（测试数据已全部清理）。

---

## 0. 一句话对照表

| 你想做到的 | 平台层能否做到 | agent 能否用 API 做 |
|---|---|---|
| 社员不能编辑「指导主文档」 | ⚠️ 只能靠**知识库粒度**只读 | ❌ 无文档级编辑权限接口 |
| 归档目录内文档只读 | ❌ 语雀没有「目录只读」 | ❌ 只有隐藏（`visible=0`） |
| 归档动作本身 | ✅ 移动目录节点即可 | ✅ `editNode` 移动节点 |
| 只允许用固定模板 / 必填不为空 | ❌ 语雀没有表单与必填校验 | ❌ 只能 agent 侧校验 + 退回 |
| 读文档全部修改时间线 | ✅ | ✅ `GET /api/v2/doc_versions` |
| 回滚被误改的文档 | ✅ | ✅ 用历史版本正文 `doc update` 覆盖 |
| 团队成员角色（管理员/成员/只读成员） | ✅ | ✅ `PUT /groups/{login}/users/{id}` |
| 知识库公开性 0/1/2 | ✅ | ✅ `PUT /repos/{id}` |
| 知识库「默认成员权限=仅查看」 | ✅ | ❌ 仅网页 UI |
| 知识库协作者（可管理/可编辑/可阅读） | ✅ | ❌ 仅网页 UI |
| 文档级「指定成员可编辑」 | ✅（分享面板） | ❌ 仅网页 UI |
| 数据表(Table) 读取 | ✅ | ✅ `body_table`（分页） |
| 数据表(Table) 创建 / 写行 | ✅（网页） | ❌ API 不支持 |

## 1. 官方 OpenAPI 的权限相关接口，一共就这些

把 26 个操作全列出来，和「权限」沾边的只有 4 个：

| 接口 | 粒度 | 说明 |
|---|---|---|
| `PUT /api/v2/groups/{login}/users/{id}` | **团队** | 改成员角色：`0` 管理员 / `1` 成员 / `2` **只读成员** |
| `DELETE /api/v2/groups/{login}/users/{id}` | 团队 | 移除成员 |
| `POST/PUT /api/v2/repos/...` | **知识库** | `public`（0 私密 / 1 公开 / 2 企业内公开）；`enhancedPrivacy` **仅创建时**可传 |
| `PUT /api/v2/repos/{id}/toc` | **目录节点** | `visible` 0/1（隐藏 ≠ 只读） |

**没有**：知识库协作者管理、知识库成员默认权限、文档级编辑权限、目录只读、模板/表单。
`groups/{login}/users` 改的是**整个团队**的角色——把社员设成「只读成员」会让他在所有知识库都失去写权限，粒度太粗，不可用。

实测：

```
PUT /groups/lqogh0/users/<不存在的用户>  → 404 Not Found   （接口存在）
可见成员 67 人，role 分布 {0: 2, 1: 65}                      （0 管理员 / 1 成员）
PUT /repos/<id>  {"public": 0}  → 200，再读回 public=0 ✓     （公开性可改）
PUT /repos/<id>  {"enhancedPrivacy": false} → 200，但 GET 不回显该字段（仅创建时可靠）
```

## 2. 语雀产品侧的权限模型（需要人工配置一次）

| 层级 | 可设置 | 入口 |
|---|---|---|
| 团队 | 成员角色：管理员 / 成员 / 只读成员 | 团队设置 → 成员 |
| 知识库 | 公开性（私密/公开/企业内公开）、**增强私密性** | 知识库设置 |
| 知识库 | **默认成员权限**：仅查看 / 可编辑 / 管理员 | 知识库 → 设置 → 成员与权限 |
| 知识库 | **协作者**：可管理 / 可编辑 / 可阅读（可单独授权） | 同上 |
| 文档 | 阅读范围（仅自己 / 指定成员 / 所有人）+ 每人的查看/评论/编辑 | 文档右上角「分享」 |
| 目录节点 | 仅 `visible`（可见/不可见） | 目录右键 |

要点：

1. **知识库内没有「某些目录只读、某些目录可写」这种能力。** 一个知识库里，成员要么可编辑全部，要么只读全部。
2. **文档级权限只在「分享」面板**，而且 API 完全不暴露；能否覆盖团队成员的编辑权，需要双账号实测（见「待验证」）。
3. 语雀**没有表单**，也**没有「内容锁定 / 限制编辑」**（网上搜到的「内容锁定」是 Umo Editor，不是语雀）。

## 3. 所以「社员不能改指导文档 / 不能改归档」怎么落地

### 方案 A（推荐）：两库分离

```
团队 lqogh0 / NOVA
├── 教室申请-投稿        ← 社员可编辑（知识库默认成员权限 = 可编辑）
│   ├── 2026-W03 投稿/
│   │   ├── 张三-周三7-8节    ← 社员按模板新建的文档（agent 只读 + 校验）
│   │   └── 李四-周五5-6节
│   └── 模板说明（只读参考）
└── 教室申请-正式        ← 知识库默认成员权限 = 仅查看（社员只读）
    ├── 00-指导文档          ← 只有 agent / CAC 能写
    ├── 2026-W03 申请/
    │   ├── 张三申请单       ← agent 生成
    │   │   └── 审批日志     ← agent 维护的子文档
    │   └── 李四申请单
    │       └── 审批日志
    └── 99-归档/            ← 天然只读（整个库对社员只读）
        └── 2026-W01 ...
```

- 配套一次性人工配置：`教室申请-正式` 的知识库 → 成员与权限 → 默认成员权限 = **仅查看**；
  把 agent 的账号（token 属主，通常是 CAC/老师）加为**协作者（可管理）**。
- 这样「社员改不了指导文档」「改不了归档」同时成立，而且**平台层强制**，不依赖 agent 自律。
- 代价：社员多一个知识库的认知成本；需要在指导文档里写清楚去哪填。

### 方案 B（单库 + agent 巡检回滚）

一个库，社员可编辑；agent 做三件事：

1. **基线快照**：`GET /api/v2/doc_versions?doc_id=<指导文档>` 或保存正文哈希；
2. **巡检**：发现指导文档 / 归档目录内文档被改动 → 用 `doc_versions` 里的历史正文
   `doc update` 覆盖回滚；
3. **告警**：在文档下评论 @当事人 说明「该文档由系统维护，已还原」。

- 优点：零人工配置，纯 API 可自动化。
- 缺点：**是「事后纠正」而不是「事前阻止」**——被改坏的那段时间里，其他社员看到的是错误内容；
  且 token 属主若不是管理员，回滚可能被对方的权限挡住（同库同权限，一般可行）。
- 适合作为方案 A 的兜底（两者可叠加）。

### 方案 C（隐藏 + 移动到归档分组）

- 归档动作：`PUT /toc` + `editNode` + `node_uuid` + `target_uuid=<归档分组 uuid>`，**实测可移动**。
- 隐藏节点：`visible=0`，节点不再出现在目录里（对读者不可见），**但文档仍可被搜索/直链访问**。
- ⚠️ `visible=0` **不是只读**，只是「藏起来」。别把它当权限用。

## 4. 模板与必填校验：只能 agent 侧做

语雀能提供的「约束」只有：

| 载体 | 能约束什么 | agent 能力 |
|---|---|---|
| 普通文档（Doc） | 无 | 读 ✅ 写 ✅ 创建 ✅ |
| 表格（Sheet） | 无字段类型约束 | 读 ✅（lakesheet 解码） 写 ❌ 创建 ❌ |
| 数据表（Table） | 列有字段类型（文本/数字/日期/单选…），表结构固定，**可能**可配必填 | 读 ✅（`body_table`，带 `page`/`page_size`） 写 ❌ 创建 ❌ |

实测（写权限令牌）：

```
POST /api/v2/repos/{id}/docs  format=lake      → 200 type=Doc
POST ...                      format=html      → 200 type=Doc format=lake（被转换）
POST ...                      format=lark/table/datatable/sheet/lakesheet → 422 "要求 markdown/html/lake"
```

结论：

- **API 只能创建普通文档**；表格和数据表都必须在网页上手工建一次。
- **API 不能写表格/数据表的行**（`body_sheet`/`body_table` 只在响应里，不在请求体 schema 里）。
- 所以「固定模板 + 必填不为空」只能在 agent 侧校验：
  1. 读投稿内容（文档正文，或数据表的 `body_table`）；
  2. 校验字段齐全、日期/节次格式合法、人数是数字、必填非空；
  3. 不合格 → 写「审批日志」+ 在投稿文档下 `comment add --mention <login>` 通知本人修改；
  4. 合格 → 生成正式申请单 + 交给 `crb` 提交。

> 建议：**投稿载体用「普通文档 + 固定模板」**。理由是 ① 文档可评论、可 @人、可按周挂目录；
> ② 数据表虽然结构更硬，但 agent 不能写、不能建，且单行不能单独评论，
> 退回通知只能落到「整张表 + @人」，颗粒度差。

## 5. 修改时间线：完全够用

官方 API 提供了完整的历史版本能力（实测）：

```
GET /api/v2/doc_versions?doc_id=284885546
  → [{id, doc_id, slug, title, user_id, user:{name}, created_at, updated_at}, ...]   按时间倒序
GET /api/v2/doc_versions/{version_id}
  → {id, doc_id, title, format, body, body_md, body_html, body_asl, created_at, user}
```

**对两种 agent 形态的意义：**

| agent 形态 | 需要什么 |
|---|---|
| 常驻 / 轮询 | 可用版本列表判断「自上次审批后是否被改过」，也能回滚 |
| 定点触发（推荐） | 其实**不需要**版本：读「当前正文 + 该文档下是否已存在『审批日志』子文档」就够判断状态；版本接口只在要追溯/回滚时才调 |

> 注意：`doc_versions` 的粒度是「一次保存/发布」，不是每一次按键输入；且返回数量可能被分页，
> 别假设一次拿全。

## 6. 「审批日志」子文档命名建议

你要求一个统一名字，方便 agent 定位 + 社员一眼懂。推荐：

### 首选：`审批日志`

- 短、语义直白、可搜索；作为申请文档的子文档时上下文已经足够清楚。
- 若担心社员误改，子文档正文首行由 agent 写死一句：
  `> ⚙️ 本文件由系统自动维护，请勿手动编辑。`
- 代码里固化成常量：`APPROVAL_LOG_TITLE = "审批日志"`，避免不同 agent 会话起出不同名字。

### 备选（按需）

| 名字 | 适用 |
|---|---|
| `[系统] 审批日志` | 想让人从标题就看出是机器维护的 |
| `00-审批日志` | 想让它排在子文档列表最上面 |
| `审批回执` | 更强调「给申请人的答复」 |
| `申请处理记录` | 更正式、更像档案 |
| `处理轨迹` | 想强调时间线 |

**不建议**用 emoji 开头（搜索/排序/复制时容易出问题），也不建议每次带时间戳
（agent 需要稳定定位同一个子文档）。

## 7. 待验证（需要双账号或 Cookie 登录）

1. **文档级「分享」权限能否覆盖团队成员的编辑权** —— 需要一个非管理员账号配合实测；
   若能覆盖，就不用拆两个知识库（但 API 依然操作不了它，只能人工配）。
2. **知识库「默认成员权限 / 协作者」有没有内部接口** —— 官方 API 没有；
   Cookie 模式下值得探一次（若有，就能让 agent 自己完成权限配置）。
3. **数据表（Table）的读取** —— 官方 spec 明确支持 `body_table` + `page/page_size`，
   但当前两个团队里都没有数据表样本，未实测；等真用了数据表要补测。
4. **`visible=0` 的读者侧效果** —— API 侧确认字段生效，但「社员是否真的看不到」需要双账号看页面。
5. **回滚是否需要管理员权限** —— 用普通成员身份的 agent 能否覆盖别人的编辑，未实测。
